# 版本 2.0.5 — Krea2 INT8 显存溢出 (OOM) 修复与 16GB 显存管理架构完善（Issue #3 全面解决）

本次发布彻底修复了在 `int8` 与 `int8 (fp16 LoRA)` 模式（`unet_storage_dtype: 'int8_tensorwise'`）下载入并运行 Krea2（`SingleStreamDiT`，例如 `moodyKrea2Mix...covrot_int8.safetensors`）时触发的严重 `CUDA out of memory` 显存溢出崩溃。同时系统化对应并解决了 [Issue #3](https://github.com/ussoewwin/Stable-Diffusion-WebUI-Forge-Nunchaku/issues/3)。

---

## 1. 概述

| 项目 | 详情 |
|---|---|
| **影响范围** | Krea2 DiT 模型（`SingleStreamDiT`、`CosmosTransformer3DModel`）搭配大型多模态文本编码器（`Qwen3-VL-4B`、`Qwen3-4B`、`Gemma2-2B`）在消费级显卡（特别是 16GB 显存显卡，如 RTX 4080 / RTX 4070 Ti Super / RTX 5060 Ti）上运行的场景。 |
| **故障表象** | 模型加载阶段或采样第 0 步时直接抛出 `torch.OutOfMemoryError: CUDA out of memory`；文本编码器初始化因庞大的 host-to-device 反量化缓冲区耗时超过 30 秒；提示词编码完成后文本编码器显存无法释放，导致扩散 UNet 加载显存不足。 |
| **技术根本原因** | 5 重复合的架构瓶颈：<br>1. `SingleStreamDiT` 未被纳入 `load_unet_int8_branch` 调度列表，回退至未量化的 `manual_cast` 且 `dtype=None`，导致 224 个 INT8 量化层被作为 Unexpected keys 丢弃并以 FP32（约 48.9 GB）展开。<br>2. `split_state_dict` 对 Qwen3-VL-4B 执行了过早的 FP16 全量反量化，破坏了原生的 `comfy_quant` 布局。<br>3. CLIP 文本编码器缺失严格的 CPU 卸载契约，在 UNet 加载期间导致约 4.24 GB 显存被死锁占用。<br>4. Forge 显存管理器未对带有 `comfy_cast_weights`（`int8_ops`）的模块进行显存剖析，尝试全量常驻显存而非局部 CPU 交换。<br>5. `comfy.ops._quantized_apply` 在跨设备迁移时与 PyTorch 的 `inference_mode` autograd 版本计数器发生冲突。 |
| **核心修复方案** | 1. **算子分发**：在 `modules_forge/hswq_int8.py` 中将 `SingleStreamDiT` 与 `CosmosTransformer3DModel` 纳入量化调度，注入 `int8_ops` 并指定 `computation_dtype=torch.bfloat16`。<br>2. **原生 INT8 TE**：在 `backend/loader.py` 中为 `Qwen3_VL_4B` 保持 `comfy_quant` 布局（约 0.4 秒直接以 4.24 GB 载入），并在反量化退出时自动释放 CUDA 缓存。<br>3. **强制 CLIP CPU 卸载**：在 `backend/comfy_te_glue.py` 中强制 `offload_device = cpu`，并将 `free_memory` 联动下发至 ComfyUI 模型管理器（提示词编码后文本编码器显存从 4.24 GB 骤降至约 32.5 MB）。<br>4. **模块级 CPU 交换**：在 `backend/memory_management.py` 中支持对 `comfy_cast_weights` 模块进行显存剖析与切分（显存常驻约 11.0 GB，约 1.87 GB 驻留 CPU 内存并动态流式交换）。<br>5. **推理模式隔离**：将 `comfy.ops._quantized_apply` 封装在 `torch.inference_mode(False), torch.no_grad()` 上下文中执行。 |
| **性能实测提升** | 16GB RTX 5060 Ti 上峰值采样显存从 >24 GB（必然 OOM）压制至 **12,066 MB**；文本编码器加载耗时从约 31 秒缩短至 **0.44 秒**；端到端采样顺畅完成，无任何 NaN 现象。 |

## 2. 技术背景与根本原因深度剖析

### 2.1 Issue #3 问题陈述
正如 [Issue #3](https://github.com/ussoewwin/Stable-Diffusion-WebUI-Forge-Nunchaku/issues/3) 中所反馈，运行量化 Krea2 检查点时会触发极严重的显存溢出。Krea2 采用了庞大的 `SingleStreamDiT` 架构，包含数十个 Transformer Block，图像与文本 Token 共享统一的序列进行计算。当与高参数量的 `Qwen3-VL-4B` 文本编码器配合使用时，若无法严格执行量化和按需卸载调度，16GB 显存将极易被瞬间撑爆。

### 2.2 SingleStreamDiT 算子调度缺口
在 `modules_forge/hswq_int8.py` 中，`load_unet_int8_branch` 依靠模型类名匹配来向模型注入量化算子（`int8_ops`）：
```python
if isinstance(model, (Flux, SD3, WanVideo, HunyuanVideo)):
    ...
```
`SingleStreamDiT`（以及 `CosmosTransformer3DModel`）此前未包含在此列表中。因此，Krea2 完全绕过了 `int8_ops` 的注入逻辑，回退到 ComfyUI 原版的 `manual_cast` 且 `dtype=None`。当加载包含 INT8 量化张量的权重字典时：
1. 全部 224 个 INT8 量化权重无法与未量化的参数形状匹配，被标记为 `Unexpected keys` 予以忽略。
2. PyTorch 按照默认的 FP32（float32，每个参数 4 字节）初始化未量化层，导致模型体积膨胀至约 **48.9 GB**，瞬间触发无法恢复的 CUDA OutOfMemoryError。

### 2.3 文本编码器过早反量化开销
在 `backend/loader.py` 中，`split_state_dict` 此前会在加载时检查 state dict 中是否包含量化权重并统一调用 `dequantize_state_dict_inplace`。对于类似 `Qwen3-VL-4B` 的现代化多模态编码器：
- 将 INT8 权重反量化为未压缩的 FP16 需要一次性分配 8.1 GB 的连续显存/内存缓冲区。
- 在 Windows 环境下，主机到显卡的数据复制与格式转换导致文本编码器加载卡死 8 到 31 秒。
- 事实上，ComfyUI 原生算子已能通过 `MixedPrecisionOps` 直接原生处理 `comfy_quant` INT8 `QuantizedTensor`，全量预反量化不仅冗余，而且造成了严重的内存峰值浪费。

### 2.4 文本编码器显存残留与引擎间同步缺失
Forge 与 ComfyUI 维护着两套独立的内部内存管理缓存。当 `comfy_te_glue` 初始化 CLIP 模型时：
1. `model_options` 未显式锁定 `offload_device = cpu`，导致提示词编码结束后部分组件依然被死锁在 GPU 显存中。
2. 即便移动了 `clip.patcher`，ComfyUI 内部的 `model_management.current_loaded_models` 依然持有文本编码器的强引用，阻碍了垃圾回收。
3. 结果导致**约 4.24 GB 显存被长期白白占用**，在准备载入体积庞大的 Krea2 UNet 时仅剩约 11.8 GB 显存可用。

### 2.5 `comfy_cast_weights` 算子的模块级 CPU 交换缺失
当 Forge 载入超大扩散模型时，`backend/memory_management.py` 会计算显存预算并将模型 Block 切分至显存与系统内存（`LoadedModel`）。然而：
- 原有的参数显存剖析循环仅针对标准参数类型与 `comfy.ops.manual_cast`。
- 使用 `comfy_cast_weights`（包括 `MixedPrecisionOps` 与 `int8_ops`）的模块未被识别为可交换模块候选。
- 内存管理器尝试将整个 12.9 GB 的 UNet 全量载入显存，而在仅剩约 11.8 GB 可用显存的情况下，在首步采样前便必然触发 OOM。

### 2.6 PyTorch 推理模式版本计数器冲突
在张量设备迁移（`cpu` 至 `cuda` 或反向）期间，`comfy.ops._quantized_apply` 需要重写底层参数引用。在 PyTorch 2.4+ 环境下，在激活的 `torch.inference_mode()` 上下文中执行此类操作会直接抛出：
```text
RuntimeError: Cannot set version_counter for inference tensor
```
该异常导致卸载/交换过程异常中断，模型在显存中处于半载入的破损状态。

## 3. 核心修复方案与完整代码剖析

### 3.1 SingleStreamDiT 与 Cosmos 算子分发（`modules_forge/hswq_int8.py`）
在 `load_unet_int8_branch` 的算子注入列表中加入 `SingleStreamDiT` 与 `CosmosTransformer3DModel`：
```python
# modules_forge/hswq_int8.py
if model_cls_name in (
    "Flux", "SD3", "WanVideo", "HunyuanVideo", "Lumina2Transformer2DModel",
    "ZImageTransformer2DModel", "SingleStreamDiT", "CosmosTransformer3DModel"
):
    model.diffusion_model.set_operations(int8_ops, computation_dtype=computation_dtype)
```
确保全部 224 个线性层均以 `comfy_cast_weights` 与 `torch.bfloat16` 计算精度构建，彻底杜绝参数膨胀。

### 3.2 原生 INT8 文本编码器加载（`backend/loader.py`）
升级 `split_state_dict`，识别 ComfyUI 原生多模态文本编码器并跳过预反量化：
```python
# backend/loader.py
if guess_clip_type in ("qwen3vl_4b", "qwen3_4b", "qwen3_06b", "gemma2_2b"):
    # 跳过过早的全量反量化；ComfyUI MixedPrecisionOps 原生支持 comfy_quant
    pass
else:
    dequantize_state_dict_inplace(clip_sd, compute_dtype=computation_dtype)
```
并在 `_load_krea2_mixed_precision_unet` 中显式传递 `computation_dtype`：
```python
unet = load_unet_int8_branch(
    sd,
    unet_storage_dtype=unet_storage_dtype,
    computation_dtype=computation_dtype,
)
```

### 3.3 强制 CLIP CPU 卸载与跨引擎显存联动（`backend/comfy_te_glue.py` 与 `memory_management.py`）
在模型选项中强制锁定 CPU 卸载，并完善清理逻辑：
```python
# backend/comfy_te_glue.py
te_model_options = {
    "offload_device": torch.device("cpu"),
    "initial_device": torch.device("cpu"),
}

def offload_comfy_clip(clip_patcher):
    if clip_patcher is not None:
        import comfy.model_management as mm
        mm.unload_model_clones(clip_patcher)
        if hasattr(clip_patcher, "model"):
            clip_patcher.model.to(torch.device("cpu"))
        torch.cuda.empty_cache()
```
在 `backend/memory_management.py` 中，使 `free_memory` 联动下发至 ComfyUI：
```python
# backend/memory_management.py
def free_memory(memory_required, device, keep_loaded=[]):
    ...
    # 联动触发 ComfyUI 显存清理
    import comfy.model_management as mm
    mm.free_memory(memory_required, device)
```

### 3.4 针对 `comfy_cast_weights` 算子的层级 CPU 交换（`backend/memory_management.py`）
扩展 `build_module_profile`，测量并注册包含 `comfy_cast_weights` 的层：
```python
# backend/memory_management.py
for name, module in model.named_modules():
    if hasattr(module, "comfy_cast_weights") or hasattr(module, "weight"):
        # 剖析模块权重的显存开销
        ...
```
当剩余显存无法容纳整个 UNet 时，`LoadedModel` 对模块列表进行切分：前约 11.0 GB 层常驻 GPU 显存，超出部分（约 1.87 GB）驻留 CPU 内存并在前向传播时流式按需加载。

### 3.5 推理模式 Autograd 隔离（`backend/patch_comfy_quant_layout_fallback.py`）
对 `_quantized_apply` 进行封装，使参数版本计数器免受 PyTorch 推理模式影响：
```python
# backend/patch_comfy_quant_layout_fallback.py
def _safe_quantized_apply(fn, tensor):
    with torch.inference_mode(False), torch.no_grad():
        return _orig_quantized_apply(fn, tensor)
```
